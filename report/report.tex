\begin{abstract}
  This report presents the design of test cases for the urban delivery system described in the specification of the second project for the Software Testing and Validation course. Appropriate design strategies are applied to test the \classname{Order} and \classname{Delivery} classes at the class level, as well as the \methodname{computeDeliveryCost} and \methodname{updateItem} methods. The final section presents the TestNG implementation of eight selected test cases from the test suite of the \classname{Order} class.
\end{abstract}

\subsection{Chosen Strategy: Non-Modal Class Testing}
\label{sec:order-strategy}

The \classname{Order} class does not possess a state machine (there are no modes that alter method behaviour); its class-level behaviour is determined by a set of \emph{invariants} over its instance variables. The appropriate strategy for testing a class of this type is \textbf{Non-Modal Class Testing}, which consists of:
(i)~identifying the domains of the variables;
(ii)~determining the \emph{On}/\emph{Off} points for each invariant boundary; and
(iii)~constructing a \emph{domain matrix} with test vectors, where each test case exercises one boundary at a time, keeping the remaining variables at typical values.

\subsection{Testing strategy: Modal Class Testing}
\label{sec:delivery-strategy}

Unlike the \classname{Order} class, the \classname{Delivery} class has an explicit \emph{state machine}: its behaviour depends on the mode the delivery is in (\code{IN\_PREPARATION}, \code{READY\_TO\_DELIVER}, \code{IN\_TRANSIT}, \code{DELIVERED}, \code{NOT\_DELIVERED}, \code{CANCELLED}), and each method is valid only in a subset of these modes. The class exhibits two kinds of constraint:
\begin{itemize}
    \item \textbf{Sequence constraints} --- the validity of a method invocation depends on the sequence of prior events (for example, \methodname{assign} is only valid after \methodname{setReady} has been called, which is captured by the current mode);
    \item \textbf{Domain constraints} --- the validity (or outcome) of a method depends on the current content of the object (for example, \methodname{assign} additionally requires the courier to have fewer than $5$ deliveries assigned; \methodname{cancel} from \code{IN\_TRANSIT} branches on the number of delivery attempts; \methodname{updateItem} from \code{READY\_TO\_DELIVER} returns to \code{IN\_PREPARATION} only if the resulting quantity is positive).
\end{itemize}

\noindent The coexistence of these two kinds of constraint is the defining feature of a \emph{modal} class, and the appropriate strategy is \textbf{Modal Class Testing}.

\subsection{Chosen Strategy: Combinational Function Testing}

The selected method-scope strategy is \textbf{Combinational Function Testing}. This is the most appropriate
strategy because the method implements a business rule equivalent to a decision table: combinations of
predicates over the \classname{Order} state select one of several possible delivery fees. Domain Analysis is
then applied inside each variant to choose On and Off boundary points systematically.

is in cents, total quantity is counted in item units, and total weight is in grams. The expected delivery
cost remains in euros, as specified for \methodname{computeDeliveryCost}.

\section{Method \methodname{updateItem}}
\label{sec:updateitem}

\subsection{Chosen Strategy: Combinational State-Input Testing \& Boundary Analysis}
The behavior of the \methodname{updateItem} method depends simultaneously on the current execution mode of the \classname{Delivery} object, the properties of the input parameters, and an internal history tracking counter. Therefore, the chosen test design strategy is a combinational synthesis of \textbf{State-Based Contextual Constraints} and \textbf{Equivalence Partitioning / Boundary Value Analysis (BVA)} applied to the input variables.

The strategy systematically checks:
\begin{enumerate}
    \item \textbf{Contextual Constraints:} Allowed states (\code{IN\_PREPARATION}, \code{READY\_TO\_DELIVER}) vs. forbidden states that must safely bypass execution and throw an exception.
    \item \textbf{Input Constraints:} Item supplier compatibility, unit bounds ($1 \le Q_{item} \le 10$) , overall positive total quantity residual ($Q_{total} > 0$) , and negative input tracking for item subtraction.
    \item \textbf{History Constraints:} Safe blocking execution after exactly 3 successful updates have transpired.
\end{enumerate}

\subsection{State + Input Combinations Matrix}
Let $U$ represent the cumulative count of successful \methodname{updateItem} operations executed on a single instance ($0 \le U \le 4$). Let $Q_{item}$ represent the requested item quantity modification, and let $Q_{final\_total}$ represent the prospective aggregated total units of all items combined in the delivery after update execution.

The logical vectors governing the input domain matrix partitions are mapped below:

package supereats.tests;

import org.testng.annotations.*;
import static org.testng.Assert.*;

import supereats.core.*;

public class OrderTest {

  private static final double EPS = 1e-9;
  private Supplier s1;      // reference supplier
  private Supplier s2;      // distinct supplier
  private Client   client;
  // Items from supplier s1 (weight in grams, integer price)
  private Item i1;          // price 10
  private Item i2;          // price  5
  private Item i50;         // price 50 (for totalQty cases)

    s1     = new Supplier("Loja A");
    s2     = new Supplier("Loja B");
    client = newClient();

    i1     = new Item(100,  10, s1, "Item 1");
    i2     = new Item(200,   5, s1, "Item 2");
    i50    = new Item(150,  50, s1, "Item 50");
    iOther = new Item(100,  10, s2, "Item from another supplier");
  }

  % Helper: the existence of a Client constructor is assumed.
  private Client newClient() {
    return new Client(/* ... valid data ... */);
  }

  // -------------------------------------------------------------------------
  // SUCCESS Cases
  // -------------------------------------------------------------------------

  // TC1: valid construction - all invariants satisfied.
  @Test
  public void tc1_validConstruction() {
    Order o = new Order(client, "Street A", 5000);

    assertEquals(o.totalQuantity(), 0);
    assertEquals(o.cost(), 0.0, EPS);
    assertTrue(o.itens().isEmpty());
  }

  // TC9: addItem in an empty order with a valid quantity.
  @Test
  public void TC9AddItemEmptyOrderValidQuantity() {
    Order o = new Order(client, "Street A", 5000);

    o.addItem(i1, 1);
    assertTrue(o.contains(i1));
    assertEquals(o.quantity(i1), 1);
    assertEquals(o.cost(), 10.0, EPS);
  }

  // TC13: boundary totalQty <= 20 + floor(cost/50) (On).
  // A unit price of 1 is used to isolate the totalQty boundary without
  // violating the cost limit (I3).
  // With cost = 24 * 1 = 24, the limit is
  // 20 + floor(24/50) = 20 + 0 = 20... therefore it is necessary to raise the
  // cost enough so that the limit reaches 24:
  //   limit = 24  <=>  floor(cost/50) = 4  <=>  cost in [200, 250).
  // Cost = 240 is chosen with items of price 10 (24 units * 10 = 240),
  // keeping cost <= 1000.
  @Test
  public void TC13TotalQuantityAtDynamicLimit() {
    Order o = new Order(client, "Street A", 5000);
    // 3 items of price 10, quantities 10 + 10 + 4 = 24 units
    Item a = new Item(150, 10, s1, "A");
    Item b = new Item(150, 10, s1, "B");
    Item c = new Item(150, 10, s1, "C");

    o.addItem(a, 10);
    o.addItem(b, 10);
    o.addItem(c,  4);

    assertEquals(o.totalQuantity(), 24); // = 20 + floor (240/50) = 24
    assertEquals(o.cost(), 240.0, EPS);
  }

  // TC19: adding an item from the SAME supplier is accepted.
  @Test
  public void TC19SameSupplierIsAccepted() {
    Order o = new Order(client, "Street A", 5000);

    o.addItem(i1, 2);
    o.addItem(i2, 3); // i2 also from supplier s1

    assertTrue(o.contains(i1));
    assertTrue(o.contains(i2));
    assertEquals(o.totalQuantity(), 5);
    assertEquals(o.cost(), 2 * 10 + 3 * 5, EPS);
  }

    }
  }

    o.addItem(i1,     1); // supplier s1
    o.addItem(iOther, 1); // supplier s2 -> exception
  }
